# 🏗️ Архитектурная проблема: Влияние действий пользователя на мониторинг

## 📋 Описание проблемы

**Контекст:** Бот запущен с домашнего ПК, все компоненты работают в одном процессе.

**Проблема:** Действия пользователя (нажатие кнопок в боте) могут влиять на работу мониторинга источников, и наоборот — мониторинг может замедлять работу бота.

---

```python
async def start_monitoring(bot, interval_minutes: int = 5):
    global _monitoring_service
    _monitoring_service = _MonitoringService(bot)
    asyncio.create_task(_monitoring_service.start(interval_minutes))  # ← Fire & forget
```

## ⚠️ Проблемы текущей архитектуры

### 1. **Один event loop на всё**

Когда ты нажимаешь кнопки в боте:
- Бот обрабатывает callback query
- Если обработка занимает время (БД, сеть) — мониторинг ждёт
- Мониторинг не может запуститься "вовремя"

Когда мониторинг работает:
- Парсинг Telegram: 2-5 секунд на канал
- Парсинг YouTube: 5-10 секунд на канал (с задержками rate limiter)
- Бот "подвисает" и не отвечает на команды

### 2. **Диаграмма временной шкалы**

```
Время    Событие                          Кто ждёт?
─────────────────────────────────────────────────────────────
00:00    Ты нажал "Мои источники"         —
00:00.5  Бот начал обработку              —
00:01    Мониторинг должен запуститься    Мониторинг ждёт бота!
00:01.5  Бот закончил обработку           —
00:02    Мониторинг начал парсинг         —
00:03    Ты нажал другую кнопку           Бот ждёт мониторинг!
00:04    Мониторинг всё ещё парсит        Бот всё ещё ждёт!
00:06    Мониторинг закончил              —
00:06.5  Бот наконец ответил тебе         Ты ждал 6.5 сек!
```

### 3. **Сетевые запросы блокируют event loop**

Несмотря на то, что код async, сетевые запросы к:
- `t.me/s/username` (Telegram парсинг)
- `youtube.com/@username/videos` (YouTube парсинг)
- БД (PostgreSQL)
- Redis (FileFakeRedis)

...могут занимать время и блокировать другие задачи.

### 4. **Rate Limiter усугубляет проблему**

```python
# Token Bucket: 10 запросов/сек для Telegram
# Но если 10 каналов одновременно:
for source in sources:  # 10 источников
    await get_telegram_posts(...)  # Каждый ждёт токен!
```

**Результат:** Мониторинг может занять 30-60 секунд вместо 5-10.

## 🔧 Возможные решения

### **Вариант 1: Отдельный процесс для мониторинга** ⭐ РЕКОМЕНДУЕТСЯ

**Суть:** Запускать мониторинг как отдельный скрипт `monitoring.py`

**Преимущества:**
- ✅ Полная изоляция: бот и мониторинг не влияют друг на друга
- ✅ Если мониторинг "упадёт" — бот продолжит работать
- ✅ Можно запустить на другом ядре CPU
- ✅ Легко масштабировать (например, на другой сервер)
- ✅ Разные логи, разное время перезапуска

**Недостатки:**
- ❌ Нужно запускать два процесса
- ❌ Нужно общее подключение к БД/Redis
- ❌ Сложнее отладка (два окна терминала)

**Реализация:**
```bash
# Терминал 1: Бот
python bot/main.py

# Терминал 2: Мониторинг
python core/services/monitoring_runner.py
```

**Файл `core/services/monitoring_runner.py`:**
```python
"""Отдельный скрипт для запуска мониторинга."""
import asyncio
from core.database import init_db
from core.redis_client import redis_client
from core.settings import settings
from core.services.monitoring.base import MonitoringService
from aiogram import Bot

async def main():
    await init_db()
    await redis_client.init()
    
    bot = Bot(token=settings.BOT_TOKEN)
    monitoring = MonitoringService(bot)
    
    await monitoring.start(interval_minutes=5)

if __name__ == "__main__":
    asyncio.run(main())
```

### **Вариант 2: Отдельный event loop в потоке**

**Суть:** Запускать мониторинг в отдельном thread + event loop

**Преимущества:**
- ✅ Один процесс (проще запуск)
- ✅ Изоляция event loops
- ✅ Бот не блокируется мониторингом

**Недостатки:**
- ❌ Сложнее отладка (потоки)
- ❌ Общие ресурсы (БД, сессии) могут конфликтовать
- ❌ Нужно аккуратно передавать bot между потоками

**Реализация:**
```python
# bot/main.py
import threading

def run_monitoring_in_thread(bot):
    def run():
        loop = asyncio.new_event_loop()
        asyncio.set_event_loop(loop)
        monitoring = MonitoringService(bot)
        loop.run_until_complete(monitoring.start(interval_minutes=5))
    
    thread = threading.Thread(target=run, daemon=True)
    thread.start()

# В on_startup:
run_monitoring_in_thread(bot)
```

### **Вариант 3: Приоритизация задач (asyncio.PriorityQueue)**

**Суть:** Сделать так, чтобы обработка сообщений бота имела приоритет над мониторингом

**Преимущества:**
- ✅ Один процесс, один event loop
- ✅ Бот всегда отвечает быстро
- ✅ Мониторинг работает в "свободное время"

**Недостатки:**
- ❌ Сложная реализация
- ❌ Мониторинг может сильно задерживаться
- ❌ Нужно переписывать всю архитектуру мониторинга

---

### **Вариант 4: Celery / RQ (очереди задач)**

**Суть:** Вынести мониторинг в очередь задач (Celery + Redis)

**Преимущества:**
- ✅ Полная изоляция
- ✅ Масштабируемость
- ✅ Отслеживание статуса задач
- ✅ Повторные попытки при ошибках

**Недостатки:**
- ❌ Нужен отдельный worker процесс
- ❌ Усложнение архитектуры
- ❌ Для домашнего ПК — overkill

## 🎯 Рекомендация для домашнего ПК

**Выбрать Вариант 1: Отдельный процесс**

**Почему:**
1. **Простота:** Два скрипта, два терминала
2. **Надёжность:** Если мониторинг упадёт — бот работает
3. **Изоляция:** Никаких конфликтов ресурсов
4. **Логирование:** Разные логи для бота и мониторинга
5. **Перезапуск:** Можно перезапустить мониторинг без перезапуска бота

**Что нужно сделать:**
1. Создать `core/services/monitoring_runner.py`
2. Обновить `bot/main.py` — убрать запуск мониторинга
3. Создать `.bat` файл для запуска обоих процессов (Windows)
4. Обновить документацию
