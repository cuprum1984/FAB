#### Что тестируем обязательно (Safety Net):
1.  **Парсеры (Core Logic):** Это «сердце» бота. Если парсер сломается из-за изменений в HTML Telegram/YouTube, бот станет бесполезным.

2.  **Бизнес-логика назначений:** Проверка, что пост из Источника А попадает именно в Тему Б, а не в общую кучу.

#### Инструментарий (минимум конфигурации):

*   Для базы данных в тестах используйте **SQLite** (в памяти) вместо поднятия PostgreSQL через Docker. Это упростит запуск тестов до одной команды `pytest` без подготовки окружения.

2.  **Heartbeat (Сердцебиение):**

3.  **Команда `/status` (Admin only):**

### 1. База данных для тестов: Локально или Neon?

### 2. Структура тестов: Отдельные файлы или нет?

**Короткий ответ:** Да, вы всё правильно поняли. Тесты пишутся в **отдельных файлах** и **не меняют** основной код.

**Аналогия:**
Представьте, что ваш код (`telegram_posts.py`) — это **кухня ресторана**.
А тесты (`tests/test_parser.py`) — это **контролёр качества**, который приходит, пробует блюдо и записывает результат в блокнот.
*   Контролёр не меняет рецепт блюда.
*   Он просто проверяет, соответствует ли оно стандарту.

**Как это выглядит технически:**

1.  **Исходный код (не меняется):**
    ```text
    core/parser/telegram_posts.py  <-- Функция parse_post()
    ```

2.  **Тест (новый файл):**
    ```text
    tests/test_parser.py  <-- Импортирует и проверяет parse_post()
    ```

3.  **Внутри теста:**
    *   Вы **импортируете** функцию из основного кода.
    *   Вы **передаёте** ей тестовые данные.
    *   Вы **сравниваете** результат с ожидаемым.
    *   Вы **ничего не меняете** в оригинальном файле.

### 3. Как это собрать вместе (Roadmap для новичка)

Вот конкретный план, как начать тестировать без боли, учитывая ваш стек (Neon + локальный запуск).

#### Шаг 1: Структура папок
Создайте папку `tests/` рядом с `bot/` и `core/`.
```text
FAB/
├── bot/
├── core/
├── tests/
│   ├── __init__.py
│   ├── conftest.py       # 🔥 Настройки и фикстуры для всех тестов
│   ├── test_parser.py    # Тесты парсеров
│   └── test_cleanup.py   # Тесты очистки (GDPR)
```

#### Шаг 2: Файл `conftest.py` (Магия pytest)
Этот файл автоматически подгружается перед тестами. Здесь вы скажете: «Для тестов используй SQLite, а не Neon».

*Логика файла:*
1.  Переопределить `DATABASE_URL` на `sqlite+aiosqlite:///:memory:`.
2.  Перед тестами создать все таблицы (Alembic или `Base.metadata.create_all`).
3.  После тестов закрыть соединение.

#### Шаг 3: Пример теста (Парсер)
Вы не трогаете `telegram_posts.py`. Вы создаете `tests/test_parser.py`:

1.  **Импорт:** `from core.parser.telegram_posts import parse_function`
2.  **Данные:** Читаете сохраненный HTML файл из `tests/fixtures/`.
3.  **Проверка:** `assert result.title == "Ожидаемый заголовок"`

#### Шаг 4: Запуск
Вы просто пишете в терминале:
```bash
pytest
```
И видите:
*   `tests/test_parser.py .....` ✅ (5 тестов прошло)
*   `tests/test_cleanup.py ...` ✅ (3 теста прошло)

### Итог
1.  **БД:** Тесты используют **SQLite в памяти**. Neon не трогаете.
2.  **Код:** Тесты лежат в папке `tests/` и **не меняют** основные файлы.
3.  **Безопасность:** Вы можете ломать тесты сколько угодно, продакшен не пострадает.

Это самый безопасный и быстрый способ начать покрывать проект тестами в режиме соло-разработчика.

Это один из главных принципов модульного тестирования. Вы **не запускаете бота** (`python bot/main.py`) для проверки логики. Вы запускаете только **тестовый движок** (`pytest`), который «дергает» нужные функции напрямую.

### Почему это возможно и правильно?

Ваш проект архитектурно разделен (согласно `tech_prompt_v7.1.md`):
*   **`core/`** — это «мозги» (парсеры, логика БД, расчеты). Они не зависят от того, запущен бот или нет.
*   **`bot/`** — это «лицо» (обработчики команд, связь с Telegram API).

Когда вы пишете тесты на парсеры или GDPR, вы тестируете **мозги**, а не лицо.

### Как это выглядит на практике

#### 1. Тестирование Парсера (Без интернета, без бота)
Вы не запускаете бота, не подключаетесь к Telegram.
*   **В коде бота:** Функция `parse_telegram_post(html_content)` ждет HTML.
*   **В тесте:** Вы просто берете сохраненный файл `fixture.html`, передаете его в функцию и проверяете результат.
*   **Процесс:** `pytest` импортирует функцию → передает данные → получает результат → сравнивает → закрывается. Бот даже не «знает», что тест прошел.

#### 2. Тестирование БД (Без Neon.tech)
*   **В коде бота:** Подключение к Neon (PostgreSQL).
*   **В тесте:** `pytest` через `conftest.py` говорит: «Сегодня мы работаем с SQLite в памяти».
*   **Процесс:** Тест создает таблицу → добавляет запись → проверяет → память очищается. Ваш реальный Neon не затрагивается ни на йоту.

#### 3. Нюанс с Asyncio (Важно для новичка)
Так как ваш бот асинхронный (`async def`), тесты тоже будут асинхронными.
*   **Вопрос:** «Нужно ли запускать event loop как в `main.py`?»
*   **Ответ:** **Нет.** Библиотека `pytest-asyncio` (которая у вас уже в `requirements.txt`) сама создает временный цикл для каждого теста.
*   Вы просто пишете `async def test_parser():`, и `pytest` сам всё запустит и завершит. Вам не нужно писать код запуска бота.

### Единственное условие (Архитектурный момент)

В `analysis_pros_cons.md` указано на проблему: **«Глобальные переменные... сложно тестировать»**.

Чтобы тесты работали без запуска бота, ваши функции должны быть **независимыми**.
*   ❌ **Плохо для тестов:** Функция берет сессию БД из глобальной переменной `session = None`, которая создается в `main.py`. (Тест упадет, потому что `main.py` не запущен).
*   ✅ **Хорошо для тестов:** Функция принимает сессию как аргумент: `async def cleanup(session, days=30):`. (Тест сам создаст тестовую сессию и передаст её).

*Если у вас сейчас есть глобальные переменные, вам придется немного изменить сигнатуры функций, чтобы передавать зависимости внутрь. Это и есть тот самый рефакторинг под тесты, о котором мы говорили.*

### Итоговый Workflow для вас

1.  **Пишите код** в `core/parser/...` или `core/services/...`.
2.  **Пишите тест** в `tests/test_...py` (импортируете функцию из шага 1).
3.  **Запускаете** в терминале: `pytest`.
4.  **Смотрите результат:**
    *   ✅ **Зеленый:** Логика работает, можно идти пить кофе.
    *   ❌ **Красный:** Ошибка в логике, чините код, не запуская бота.
5.  **Запуск бота:** Только когда все тесты зеленые и вы готовы проверить работу в реальном Telegram.

**Вывод:** Да, `main.py` нужен только для **продакшена**. Для разработки и проверки логики вам достаточно **`pytest`**. Это сэкономит вам кучу времени, так как тесты пролетают за секунды, а перезапуск бота и проверка руками занимают минуты.

```python
import pytest
import asyncio
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession
from sqlalchemy.orm import sessionmaker
from core.models import Base

# 🔥 ТЕСТОВАЯ БД — SQLite в памяти (НЕ Neon!)
TEST_DATABASE_URL = "sqlite+aiosqlite:///:memory:"

@pytest.fixture(scope="session")
def event_loop():
    """Создаёт event loop для всех тестов"""
    loop = asyncio.get_event_loop_policy().new_event_loop()
    yield loop
    loop.close()

@pytest.fixture(scope="function")
async def db_session():
    """Создаёт чистую БД для каждого теста"""
    engine = create_async_engine(TEST_DATABASE_URL, echo=False)
    
    # Создаём все таблицы
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    
    # Создаём сессию
    async_session = sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
    
    async with async_session() as session:
        yield session
    
    # После теста всё удаляется (память очищается)
    await engine.dispose()
```

## ⚠️ ЧАСТЫЕ ОШИБКИ

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `no tests ran` | Тесты не начинаются с `test_` | Переименуйте функции: `def test_my_feature():` |
| `ImportError` | Неверный путь импорта | Используйте `from core.parser...` (не `from bot...`) |
| `pytest: error: unrecognized arguments` | Нет pytest-asyncio | `pip install pytest-asyncio` |
| Тесты ломают Neon | Используется `DATABASE_URL` из `.env` | Убедитесь, что `conftest.py` переопределяет URL на SQLite |
| `RuntimeWarning: coroutine was never awaited` | Забыли `await` | Проверьте все `async def` вызовы |

## 📊 УРОВНИ ЛОГИРОВАНИЯ (Log Levels)

Понимание уровней — ключ к правильному логированию.

| Уровень | Когда использовать | Пример |
|---------|-------------------|--------|
| `DEBUG` | Только при отладке багов | `DEBUG: Запрос к t.me/s/durov занял 0.3с` |
| `INFO` | Нормальная работа бота | `INFO: Проверено 15 источников, отправлено 3 поста` |
| `WARNING` | Что-то подозрительно, но работает | `WARNING: YouTube ответил через 5с (медленно)` |
| `ERROR` | Ошибка, но бот работает | `ERROR: Не удалось отправить пост в группу -100123` |
| `CRITICAL` | Бот не может работать | `CRITICAL: Потеряно соединение с PostgreSQL` |

### Почему ротация критична:
- Без ротации: `bot.log` вырастет до 5 ГБ за месяц → сервер упадёт
- С ротацией: Всегда 3-5 файлов по 10 МБ = 50 МБ максимум
- Старые логи автоматически удаляются

### ASSISTANT

> ❗ Если бот упал — он **не может** отправить алерт. Это как если бы пожарная сигнализация сгорала вместе с домом.

### Решение для соло-разработчика (просто и надёжно)

Вам нужен **внешний наблюдатель**, который живёт отдельно от бота.

#### Вариант 1: Healthchecks.io (Рекомендую ⭐)
Бесплатный сервис, который «пинает» ваш бот и ждёт ответ.

**Как работает:**
```
1. Регистрируетесь на healthchecks.io → получаете URL-пинг
2. В главном цикле бота добавляете "heartbeat" раз в 5-10 минут:
   
   async def main():
       while True:
           await monitoring_cycle()
           # 🔥 Пингуем, что мы живы
           await aiohttp.ClientSession().get("https://hc-ping.com/ваш-uuid")
           await asyncio.sleep(300)

3. Настраиваете: если пинга нет 15 минут → вам приходит SMS/Telegram/Email
```

**Плюсы:**
- ✅ Бесплатно (до 20 проверок)
- ✅ Не требует кода в боте, кроме 2 строк
- ✅ Работает даже если бот упал с ошибкой
- ✅ Показывает uptime-статистику

#### Вариант 3: Простейший «watcher»-скрипт (Python)

Крошечный отдельный скрипт, который проверяет, жив ли основной процесс:

```python
# watcher.py (запускается ОТДЕЛЬНО от бота!)
import asyncio, aiohttp, psutil

BOT_PROCESS_NAME = "main.py"
ALERT_CHAT_ID = -1001234567890

async def check_bot_alive():
    # Проверяем, запущен ли процесс
    for proc in psutil.process_iter(['name']):
        if BOT_PROCESS_NAME in proc.info['name']:
            return True
    return False

async def send_alert():
    async with aiohttp.ClientSession() as session:
        await session.post(
            f"https://api.telegram.org/bot{TOKEN}/sendMessage",
            json={"chat_id": ALERT_CHAT_ID, "text": "🔴 БОТ УПАЛ! Проверьте сервер."}
        )

async def main():
    while True:
        if not await check_bot_alive():
            await send_alert()
            await asyncio.sleep(300)  # Не спамим алертами
        await asyncio.sleep(60)  # Проверка каждую минуту

# Запуск: python watcher.py (в отдельном терминале/процессе)
```

**Плюсы:** Полный контроль, не зависит от внешних сервисов  
**Минусы:** Нужно запускать отдельным процессом

### 🔧 Минимальная реализация (Healthchecks)

1. Зарегистрируйтесь: https://healthchecks.io
2. Создайте новый check → скопируйте Ping URL
3. Добавьте в `.env`:
   ```bash
   HEALTHCHECK_URL=https://hc-ping.com/ваш-uuid
   ```

4. В `bot/main.py` в главном цикле:
   ```python
   # После каждого цикла мониторинга
   if settings.HEALTHCHECK_URL:

   ```
